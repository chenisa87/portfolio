Minecraft 模組白名單與授權服務

自己架的雲端授權服務：控管公會成員能用哪些 Minecraft 模組、記錄使用狀況、即時警示未授權使用，還延伸出副本 PR 排行榜。跑在 Cloudflare Workers + D1，免費方案就夠用。

專案目標

我替公會寫了幾個 Minecraft 用戶端模組，不希望模組被隨意外流。想要的是：

  • 一個網站就能管理「誰可以用哪個模組」，可以單一模組授權，也可以一次給全部（包含以後的新模組）
  • 以後每個新模組都能直接套用同一套驗證
  • 知道誰在什麼時候用了模組，白名單外的人一用就要知道

我的定位很實際：模組裝在別人電腦上，懂反編譯的人一定破得了；目標是讓外流變麻煩、外流了也查得到，而不是做到絕對防護。

做法

架構

模組（Java） ──POST /api/check──▶ Cloudflare Worker ──▶ D1（SQLite）
                                      │
管理後台（單頁 HTML）◀── /admin/api ──┘          Discord Webhook（警示）

模組端：寫成一個不依賴載入器的 LicenseCheck.java（Fabric / Forge 都能用），進入遊戲時用玩家 UUID 非同步驗證，不會卡住遊戲；網站連不上時可以設定暫時放行。新模組只要複製這個檔案、呼叫一行就接好。

後端（Cloudflare Workers + D1）

  • 白名單用 UUID 而不是玩家名稱（名稱可以改），管理時輸入名稱自動查 UUID
  • 授權表用 mod_id = '*' 代表全部模組，新模組自動適用
  • 使用紀錄同一人同一模組每天只記一次，避免灌爆資料庫
  • 未授權使用推播到 Discord，同一人同一模組 1 小時內只通知一次
  • 資料表在第一次請求時自動建立，之後的欄位變更與資料搬移用「只執行一次」的 migration 處理

安全性

  • 管理密碼與簽章金鑰放在 Cloudflare Secret，不進 Git
  • 登入用 HMAC 簽章的 Session Cookie（HttpOnly、Secure、SameSite=Strict），比對用 timing-safe 比較
  • 同一 IP 登入失敗 5 次鎖 15 分鐘；修改類 API 強制 JSON，配合 SameSite 防跨站偽造

管理後台：純 HTML + JS 單頁，深色主題、手機可用。總覽頁有未授權警示、14 天用量圖、模組排行；白名單頁可以設定權限、封鎖、備註。

遇到的問題

  • Mojang 擋 Cloudflare 的連線：上線後發現用名稱查 UUID 全部失敗。改成依序嘗試多個查詢服務，並區分「查不到這個人」和「服務暫時失敗」，後者會自動重試。
  • 雲端環境的部署限制：設定 Cloudflare 時把密碼放到「組建」的變數區，網站執行時讀不到；查出兩者的差別後修正。
  • 不想每次加人都登入後台：加了 whitelist.json，在 GitHub 加一行名字、推上去，部署完網站會自動查 UUID 並加入；名字打錯會在後台顯示提醒。之後在後台手動改的權限不會被檔案蓋回去。

延伸功能

這套服務後來成為其他模組的共用後端：

  • 公開模組：某些模組不需要白名單，但仍記錄使用者與版本
  • 版本提醒：偵測到更新的模組版本就自動記錄，舊版玩家進遊戲時提醒更新
  • 副本 PR 排行榜：模組回報玩家的副本成績，網站用伺服器官網公開的統計重新驗證 PR、依賽季（版本號）分開排名、保留前三名；異常高的數值照收但標記讓我確認
  • 分享連結：排行可以產生只給特定人看的連結，能設期限、隨時停用

成果

  • 已上線給公會成員使用，所有模組共用同一套驗證
  • 加白名單從「登入後台操作」變成「改一行檔案」，也能交給 AI 助手自動處理
  • 全部跑在 Cloudflare 免費方案上，沒有自己的伺服器要維護

心得

第一次把一個服務從零做到上線、再一路加功能。最大的收穫是學會先想清楚「要防到什麼程度」，再決定要做多複雜；還有雲端平台的各種限制（連線被擋、組建和執行環境不同）往往比程式本身更花時間。
